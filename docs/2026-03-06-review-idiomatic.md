# R9 Idiomatic Review — F-044 Macro + Dialect Trait

## Summary

The F-044 refactoring introduces a `SqlDialect` trait with 3 implementations (SQLite, PostgreSQL, MySQL), an `impl_metadata_provider!` macro for read-path deduplication, and 6 writer macros (`impl_recompute_table_column_stats`, `impl_writer_query_ops`, `impl_writer_file_ops`, `impl_writer_ddl_ops`, `impl_writer_drop_inner`, `impl_writer_drop_ops`) for write-path deduplication. The approach successfully eliminates significant code duplication across the 3 SQL backends.

Overall, the design is sound and pragmatic. The trait + macro combination is a reasonable approach for this problem domain where sqlx's type system makes generic trait implementations impractical. The findings below are primarily P2/P3 quality and performance improvements.

## Findings

### R9-I-001: `ph()` returns `String` for constant values (Priority: P2)
**File**: `src/dialect.rs:6,78,195,297`
**Description**: `SqliteDialect::ph()` and `MySqlDialect::ph()` always return `"?"` regardless of `n`, allocating a new `String` every call. For SQLite, `ph()` is called 6-8 times per method in `impl_metadata_provider!` alone (~20+ methods), meaning dozens of heap allocations for a constant value. PostgreSQL genuinely needs `format!("${n}")`, but SQLite and MySQL do not.
**Suggested fix**: Return `Cow<'static, str>` instead of `String`. SQLite/MySQL return `Cow::Borrowed("?")`, PostgreSQL returns `Cow::Owned(format!("${n}"))`. Alternatively, keep `String` but add a `const PH: &str = "?"` approach and let the macros use `d.ph(n)` only for PG, with a literal `"?"` for the others — but `Cow` is cleaner.
**Effort**: S

### R9-I-002: Many dialect methods allocate where `Cow` or `&'static str` would suffice (Priority: P3)
**File**: `src/dialect.rs:86,107-113,115-116,147,152-153,157,264-266,269-271,329-330,334,365-366,371`
**Description**: Methods like `col()`, `cast_text()`, `cast_int()`, `clamp_zero()`, `read_uuid()`, `uuid_ph()`, and `greatest()` frequently return `String` even when one or more dialect implementations return a constant or the input unchanged. Examples:
- `SqliteDialect::col(name)` → `name.to_string()` (identity clone)
- `SqliteDialect::cast_int(expr)` → `expr.to_string()` (no-op cast)
- `SqliteDialect::read_uuid(col)` → `col.to_string()` (identity)
- `MySqlDialect::uuid_ph()` → `"?".to_string()` (constant)

These are all called inside SQL-building `format!()` strings, so the allocations are consumed immediately and discarded.
**Suggested fix**: Return `Cow<'_, str>` for methods that sometimes return the input unchanged. For hot paths, this avoids one allocation per call. For cold DDL paths, this is a nit.
**Effort**: M (many signatures to change)

### R9-I-003: `SqlDialect` uses instance methods on zero-sized types (Priority: P3)
**File**: `src/dialect.rs:4,75,192,294`
**Description**: `SqliteDialect`, `PostgresDialect`, and `MySqlDialect` are all unit structs (zero-sized). All trait methods take `&self` but never use `self`. These could be associated functions, but the trait requires `&self` for dynamic dispatch. Since these are used as concrete types (not `dyn SqlDialect`), `&self` is unnecessary overhead — the compiler will optimize it away, but it's semantically misleading.
**Suggested fix**: This is fine as-is. The trait design is future-proof if dynamic dispatch is ever needed. No change recommended — noting for completeness.
**Effort**: N/A

### R9-I-004: `#[allow(dead_code)]` on `SqlDialect` trait and all dialect structs (Priority: P2)
**File**: `src/dialect.rs:3,74,191,293`
**Description**: The trait and all three structs have `#[allow(dead_code)]`. This blanket suppression masks genuine dead code warnings. The `#[allow(dead_code)]` on the trait itself (line 3) is concerning — if a method truly becomes unused, the warning is suppressed and dead code accumulates silently. The struct-level `#[allow(dead_code)]` suggests they may only be used inside macros, which the compiler can't trace.
**Suggested fix**: Remove `#[allow(dead_code)]` from the trait definition. Keep it on structs if needed (macro usage confuses the compiler). Alternatively, use `#[cfg_attr(not(feature = "write"), allow(dead_code))]` to suppress only when write features are disabled, since write-only methods like `uuid_value()`, `greatest()`, etc. are legitimately dead without `write`.
**Effort**: S

### R9-I-005: Repeated `use crate::dialect::SqlDialect;` inside every macro method body (Priority: P3)
**File**: `src/metadata_provider_impl.rs:25,51,84,118,154,201,293,330,370,422,472,533,633,689,730,785,826,864,900,940`
**Description**: Every method generated by `impl_metadata_provider!` contains `use crate::dialect::SqlDialect;` at the top. This is repeated 20+ times within the macro expansion. Rust macros expand in the caller's scope, so a single `use` at the top of the `impl` block would suffice.
**Suggested fix**: Move `use crate::dialect::SqlDialect;` to the top of the macro-generated `impl MetadataProvider for $struct_name { ... }` block, before the first method. This eliminates ~20 redundant imports per expansion (3 backends = ~60 total). Similarly for `impl_writer_query_ops!`, `impl_writer_file_ops!`, etc.
**Effort**: S

### R9-I-006: Dialect is re-instantiated as `let d = $dialect;` in every method (Priority: P3)
**File**: `src/metadata_provider_impl.rs:26,51,84,...` and `src/metadata_writer_impl.rs:16,148,...`
**Description**: Every macro-generated method creates a fresh dialect instance with `let d = $dialect;`. Since dialects are zero-sized unit structs, the optimizer will elide this. However, the pattern is noisy and could be simplified.
**Suggested fix**: No code change needed — the compiler optimizes this perfectly. Just noting the pattern for documentation.
**Effort**: N/A

### R9-I-007: `next_id_sql()` panics on unknown entity (Priority: P2)
**File**: `src/dialect.rs:184,286`
**Description**: `SqliteDialect::next_id_sql()` and `PostgresDialect::next_id_sql()` panic with `panic!("unknown entity for next_id_sql: {entity}")` on unrecognized entity names. While this is only called from macro-generated code with known string literals, a panic in library code is not idiomatic Rust. If someone extends the system and adds a new entity, they get a runtime panic instead of a compile-time error.
**Suggested fix**: Return `Result<(String, bool)>` and propagate the error, or use an enum instead of a string for entity names. If keeping strings, at least use `unreachable!()` with a clear comment that the inputs are compile-time constants.
**Effort**: S

### R9-I-008: `MySqlDialect::next_id_sql()` is a dead stub (Priority: P2)
**File**: `src/dialect.rs:380-386`
**Description**: `MySqlDialect::next_id_sql()` returns `("SELECT 0".to_string(), false)` with a comment "MySQL uses next_sequence_id() function instead". The method exists only for "trait completeness" but is never meaningfully called. This is confusing — someone reading the trait would assume all methods are used by all backends.
**Suggested fix**: Either: (a) make `next_id_sql()` return `Option<(String, bool)>` so MySQL can return `None`, or (b) add a `/// # Panics` / `unimplemented!()` to make it clear this is intentionally unused, or (c) move ID allocation out of the dialect trait entirely since it's a backend-specific concern, not a SQL dialect concern.
**Effort**: S

### R9-I-009: `impl_writer_ddl_ops!` contains massive DDL snapshot boilerplate (Priority: P2)
**File**: `src/metadata_writer_impl.rs:1092-1852`
**Description**: The DDL snapshot creation pattern (get max schema_version, insert snapshot, insert schema_version record) is repeated verbatim 7 times within `impl_writer_ddl_ops!` (create_view, drop_view, rename_view, alter_table, rename_table, set_table_comment, set_column_comment). The same pattern also appears in `impl_writer_drop_inner!`. This is ~30 lines of identical code per occurrence (~210 lines total), all within the same macro.
**Suggested fix**: Extract a helper function `create_ddl_snapshot(tx, dialect) -> Result<i64>` that handles the common snapshot+schema_version pattern. This could be a macro-internal function or an async helper method on the struct (via another small macro). This would reduce the DDL macro by ~180 lines.
**Effort**: M

### R9-I-010: `unwrap()` in macro-generated DDL code (Priority: P2)
**File**: `src/metadata_writer_impl.rs:1154`
**Description**: In `create_view()`:
```rust
.map(|r| r.try_get::<String, _>(0).unwrap_or_default())
.unwrap_or_default();
```
The inner `unwrap_or_default()` on `try_get` silently converts a deserialization error into an empty string. This is used for the `schema_name` in `changes_made` formatting. While not a data corruption risk, it masks errors — a corrupt `schema_name` column would silently produce `""` in the changelog rather than propagating the error.
**Suggested fix**: Use `?` to propagate the `try_get` error, or at minimum log a warning.
**Effort**: S

### R9-I-011: `#[allow(unused_variables)]` for `last_id_fn` in file ops macro (Priority: P3)
**File**: `src/metadata_writer_impl.rs:462,628,832,1022`
**Description**: `let last_id_fn = $last_id;` is guarded by `#[allow(unused_variables)]` because SQLite/PG don't use it (they use RETURNING). The variable is created but may never be called. This is a minor code smell — the pattern works but is not self-documenting.
**Suggested fix**: Consider using `let _last_id_fn = $last_id;` only in the RETURNING branch, or restructure so the closure is only captured when `!d.supports_returning()`. Alternatively, this is fine as-is — the compiler eliminates the dead code.
**Effort**: S

### R9-I-012: Macro error messages will be hard to debug (Priority: P2)
**File**: `src/metadata_writer_impl.rs` (all macros)
**Description**: When a sqlx type mismatch occurs inside a macro-generated method (e.g., binding wrong type), the compiler error will point to the macro invocation site (e.g., `metadata_writer_sqlite.rs:919`) rather than the actual problematic line in the macro definition. With 2000+ lines of macro definitions, diagnosing "expected SqliteRow, found PgRow" type errors requires manual macro expansion. This is an inherent limitation of Rust macros.
**Suggested fix**: No practical fix. Document this in the macro file header: "To debug type errors in macro-generated code, use `cargo expand --lib` to see the expanded code." Consider adding `// MACRO: impl_writer_file_ops` comments at invocation sites for grep-ability.
**Effort**: S (documentation only)

### R9-I-013: `pool_type` macro parameter is accepted but never used (Priority: P2)
**File**: `src/metadata_provider_impl.rs:10`, `src/metadata_writer_impl.rs:141,370,1085,2172`
**Description**: Several macros accept `pool_type = $pool_type:ty` but never reference `$pool_type` in the macro body. The macro relies on `self.pool` existing on the struct, and sqlx's type inference handles the rest. The parameter exists for documentation/symmetry but is dead.
**Suggested fix**: Either remove `pool_type` from macro parameters (simpler), or use it in type annotations for clarity (e.g., `let pool: &$pool_type = &self.pool;`). Removing is cleaner — if a struct has the wrong pool type, the compiler will catch it when `sqlx::query()` is called.
**Effort**: S

### R9-I-014: `list_views` uses `.iter().map()` instead of `.into_iter().map()` (Priority: P3)
**File**: `src/metadata_provider_impl.rs:881`
**Description**: `list_views` uses `rows.iter().map(...)` while all other methods use `rows.into_iter().map(...)`. This borrows `rows` instead of consuming it, meaning the `Vec<Row>` stays alive until the closure completes. While functionally equivalent here, it's inconsistent with the rest of the macro.
**Suggested fix**: Change `.iter()` to `.into_iter()` for consistency.
**Effort**: S

### R9-I-015: `quote_identifier` vs `quote_mysql_identifier` vs `SqlDialect::quote_id` (Priority: P2)
**File**: `src/metadata_provider_sqlite.rs:238`, `src/metadata_provider_postgres.rs:251`, `src/metadata_provider_mysql.rs:257,261`, `src/dialect.rs:82,199,301`
**Description**: There are now three ways to quote identifiers:
1. `SqlDialect::quote_id()` — the new trait method
2. `quote_identifier()` — standalone function in `metadata_provider.rs` (used by override methods)
3. `quote_mysql_identifier()` — MySQL-specific standalone function

The dialect trait should be the single source of truth, but the override methods (`get_inlined_data_impl`, `get_delete_files_impl`) still use the old standalone functions. This creates inconsistency — some code uses the trait, some uses the standalone functions.
**Suggested fix**: Migrate the override methods to use the dialect's `quote_id()`. This would make `quote_identifier()` and `quote_mysql_identifier()` dead code that can be removed. However, since these override methods aren't macro-generated, they'd need to construct the dialect locally.
**Effort**: M

### R9-I-016: `metadata_writer_impl.rs` is 2294 lines — approaching maintainability limits (Priority: P3)
**File**: `src/metadata_writer_impl.rs`
**Description**: The writer macro file is 2294 lines across 6 macros. While each macro is well-documented, the file is large enough that navigating between macros requires scrolling past hundreds of lines. The DDL macro alone is 770 lines.
**Suggested fix**: Consider splitting into `metadata_writer_impl_ddl.rs` and `metadata_writer_impl_file.rs` if the file continues to grow. Current size is borderline acceptable.
**Effort**: M

### R9-I-017: `block_on` vs `block_on_once` vs `block_on_with_retry` naming (Priority: P3)
**File**: `src/metadata_provider.rs:791`, `src/metadata_writer_sqlite.rs:58`
**Description**: `block_on_once` was created as a wrapper around `block_on` to match the `FnMut() -> Fut` signature expected by the macros (needed because `block_on_with_retry` takes closures). The name `block_on_once` doesn't clearly convey why it exists — it sounds like "run only once" rather than "adapter for macro compatibility."
**Suggested fix**: Rename to `block_on_no_retry` or add a clearer doc comment. The current doc comment references the macro pattern but could be more explicit.
**Effort**: S

### R9-I-018: `column_order_type` macro parameter is a workaround for PG schema difference (Priority: P3)
**File**: `src/metadata_writer_impl.rs:1082,1090,1388`
**Description**: The `impl_writer_ddl_ops!` macro takes `column_order_type = $co_type:ty` (i64 for SQLite/MySQL, i32 for PG) because PostgreSQL's `ducklake_column.column_order` is `INTEGER` (mapped to i32 by sqlx) while SQLite/MySQL use `INTEGER` (mapped to i64). This leaks a schema detail into the macro interface.
**Suggested fix**: Standardize on i64 everywhere by always casting: `r.try_get::<i64, _>(3)?` should work for all backends since sqlx can upcast i32 to i64. If not, use `r.try_get::<i32, _>(3)? as i64` universally. This eliminates the `column_order_type` parameter.
**Effort**: S
